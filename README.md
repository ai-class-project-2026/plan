## 2. 추진 배경과 문제 정의

### 2.1 문제


1. **일정이 대화 속에 묻힌다**: 팀플 일정은 "화요일 어때?" → "난 안 돼" → "그럼 목 7시?" → "ㅇㅋ"처럼 여러 턴에 걸쳐 정해진다. 누군가 따로 정리하지 않으면 놓치고, 번복되면 옛날 일정이 그대로 남는다.
2. **학생 공간의 욕설/비방**: 학생 커뮤니티에서는 욕설이 흔하고, 사전 기반 필터는 "ㅅ1발", "씨@발", "tlqkf" 같은 우회 표현을 못 막는다.

### 2.2 페르소나

* **팀장 민준 (고2)**: 단톡에서 정한 회의 시간을 매번 공지로 다시 정리해야 함. 빼먹으면 누군가 안 옴.
* **팀원 서연 (고2)**: 학원 때문에 시간이 자주 바뀜. "그래서 언제로 정해졌어?"를 자주 물어봄.
* **동아리 운영진 하은 (고3)**: 동아리 채팅의 욕설/비방 관리가 부담. 기존 필터는 우회 표현을 못 막음.

## 3. 경쟁 분석과 차별점

### 3.1 기존 서비스

| 서비스 | 하는 것 | 빈틈  |
|-----|------|-----|
| 잔디  | 대화방/메시지 요약, 메시지를 업무로 전환 (AI 기능은 유료 인텔리전스 플랜 전용) | 기업용 유료, 대화에서 일정을 자동 확정하지 않음 |

| 네이버 클린봇 | 기호/문자를 활용한 우회 악플까지 대응하도록 지속 업그레이드 | 네이버 서비스 내부 전용 |

### 3.2 차별점


1. 메시지 1개가 아니라 **대화 흐름 전체**를 보고 확정, 번복, 취소를 판단
2. 사전 필터가 못 잡는 **우회 욕설** 탐지 + 오탐 방지
3. 학생 팀이 **무료로** 쓰는 가벼운 협업 공간
4. 사용자 피드백으로 **AI가 계속 개선되는 구조**

## 4. 목표와 성공 기준

### 4.1 서비스 목표

* 팀원 누구도 일정을 따로 정리하지 않아도 캘린더가 최신 상태로 유지됨
* 우회 욕설이 채팅방에 노출되지 않음

### 4.2 정량 목표 (최종 평가 기준, 실제 테스트셋)

| 영역  | 지표  | 목표  |
|-----|-----|-----|
| 일정 AI | 확정 일정 F1 | 0\.90 이상 |
| 일정 AI | 오등록률 (확정 아닌 걸 확정으로 낸 비율) | 5% 이하 |
| 일정 AI | 취소 감지율 | 85% 이상 |
| 일정 AI | 응답 시간 | 3초 이내 |
| 욕설 AI | 사람 우회 테스트셋 F1 | 기존 필터 대비 +20%p 이상 |
| 욕설 AI | 오탐률 | 3% 이하 |
| 욕설 AI | 응답 시간 | 100ms 이내 (CPU) |

이 목표는 사람이 만든 테스트셋 기준이다. 그 테스트셋이 아직 없어서 달성했는지는 재지 못했다. 개발 중에 AI가 쓴 시험지로 잰 값은 0장, 8.8, 9.5에 있다.

응답 시간은 잰 값이 있다. 일정은 p95 3.77초, 평균 2.58초로 3초 목표를 넘는다 (모델을 3B에서 7B로 바꾸면서 느려졌고, 채택 기준은 p95 4초 이하로 따로 정했다). 욕설은 바로 앞 버전(v3)을 노트북 CPU에서 쟀을 때 메시지당 약 21ms였고, v4와 서비스 서버에서는 재지 않았다.

### 5.2 핵심 원칙

**AI는 자동 등록하지 않고 항상 제안만 한다.**

* 잘못 등록되는 피해를 막는다
* 사용자가 누른 버튼(추가/수정/무시)은 카드와 함께 저장된다. 평가와 재학습 데이터로 쓰려던 계획이었는데, 지금은 꺼내 쓰는 도구가 없고 동의 화면은 "AI 학습에 쓰지 않아요"라고 안내한다 (11장). 서버가 스스로 내린 카드도 "무시"로 기록돼서 사람이 누른 무시와 구분되지 않는다

## 6. 사용자 흐름

### 6.1 일정 자동 등록


1. 팀원들이 채널에서 일정 협상
2. 대화가 10초 멈추면 AI가 최근 대화를 읽고, 확정된 일정이 있으면 채팅에 "새 일정" 카드를 띄운다. 카드에는 날짜, 제목, 시각, 장소, 참석자(불참자는 줄을 그어 표시), 메모와 [캘린더에 추가] [수정] [무시] 버튼이 있다
3. [캘린더에 추가]를 누르면 캘린더에 등록된다. 누른 사람 화면에서는 카드가 "등록됨"으로 바뀌고, 다른 팀원 화면에서는 카드가 사라진다
4. 이후 시간이나 장소가 바뀌면 "일정 변경" 카드([이렇게 바꾸기] [수정] [무시])가, 취소가 확정되면 "일정 취소" 카드([일정 취소하기] [무시])가 뜬다. 취소한 일정은 지우지 않고 취소됨으로 남긴다
5. 카드가 떴는데 이어진 대화에서 그 일정이 엎어지면, 아직 아무도 답하지 않은 카드는 자동으로 내려간다 (시각이 숫자로 정해진 새 일정 카드와 변경 카드만)

**카드가 거의 맞을 때, 또는 카드가 안 떴을 때 (말로 고치기/추가하기)**

실사용 테스트에서 카드는 대부분 거의 맞았지만 한 칸이 틀리는 경우가 잦았다 (시각, 빠진 장소, 불참자가 참석자에 들어감). 합의한 일정에 카드가 아예 안 뜨는 경우도 있었다. 이때 폼을 처음부터 고치지 않고 한 줄로 말하면 되게 한다.

1. 새 일정/일정 변경 카드 아래 입력칸에 "8시로 바꿔줘, 장소는 도서관", "지호는 못 와"처럼 쓴다
2. 서버가 말한 칸만 바꾸고, 같은 카드가 모든 팀원 화면에서 바뀐 내용으로 갱신된다
3. 팀원은 평소처럼 [캘린더에 추가](변경 카드는 [이렇게 바꾸기]) / [수정] / [무시]를 누른다 (말로 고쳐도 자동 등록은 하지 않는다)
4. 카드가 안 떴으면 [일정] 버튼(채팅 입력창 왼쪽, 캘린더의 일정 추가)의 창 맨 위에 "내일 저녁 7시 도서관에서 팀 회의"처럼 쓴다. 칸이 채워지고, [추가하기]를 눌러야 저장된다

한계: 취소 카드에는 입력칸이 없다. 말로 "취소해줘"라고 하면 지우지 않고 [무시]나 캘린더의 [일정 취소]를 쓰라고 안내한다. 칸을 비우는 말("장소 빼줘")은 지원하지 않는다 (폼의 [수정]을 쓴다). 고친 카드는 AI가 처음 낸 내용도 같이 저장한다. 두 기능은 서버가 있어야 해서 데모 모드에서는 보이지 않는다.

### 6.2 욕설 필터


1. 메시지 전송 시 서버에서 판정한 뒤 저장한다
2. 욕설이면 욕 부분을 검은 줄로 가리고 "부적절한 표현이 가려졌어요 [보기]"를 붙인다. 가릴 곳이 3군데 이상이거나 글자의 절반 넘게 가려지면 메시지 전체를 가린다. 프로젝트 설정에 따라 가리지 않고 경고만 붙이거나, 방장 화면에 표시를 더한다
3. 오탐이면 [욕설 아님]으로, 미탐이면 메시지에 마우스를 올렸을 때 나오는 깃발 버튼(욕설 신고)으로 신고한다. 내가 보낸 메시지도 신고할 수 있고, 신고한 문장은 신고 기록에 같이 저장된다

## 8. AI 1: 대화 기반 일정 생성

### 8.1 태스크 정의

* **입력**: 대화 묶음 (메시지 최대 30개: 화자, 텍스트, 시각) + 기준 시각 + 참여자 목록 + 기존 캘린더 일정 (오늘 이후의 확정 일정)
* **대화 묶음**: 마지막으로 답한 카드 뒤의 메시지, 그리고 8시간 넘게 대화가 끊긴 곳 뒤의 메시지만 보낸다. AI 일정 도우미를 켠 뒤에 쓴 메시지만 쓴다
* **출력**: 일정 후보 목록과 각 후보의 상태

### 8.2 출력 형식

```
{
  "events": [
    {
      "title": "팀 회의",
      "date": "2026-10-15",
      "weekday": "목",
      "start": "19:00",
      "time_text": null,
      "location": "디스코드",
      "status": "confirmed",
      "attendees": ["민준", "서연", "지호", "하은"],
      "absent": [],
      "note": null
    }
  ]
}
```

* status: proposed(제안 중) / rejected(폐기) / confirmed(확정) / cancelled(취소)
* 시각이 숫자가 아니면 start는 null로 두고, 원문 표현은 time_text에 저장 (예: "점심시간")
* 서버는 이 일정 목록을 캘린더와 대조해 카드로 바꾼다. 카드는 새 일정(add), 일정 변경(update), 일정 취소(cancel) 세 가지다 (8.4)

### 8.3 정답 기준 가이드라인

**확정 조건 (둘 중 하나)**


1. 마지막 수정안에 대해 제안자 포함 과반이 동의하고 반대가 없음 (4명이면 3명)
2. 제안자나 팀장의 명시적 확정 선언("이걸로 확정", "그럼 그때 보자") + 1명 이상 동의

**세부 규칙**

* 불참 선언자는 absent에 넣고, 늦은 합류는 참석으로 보고 note에 기록
* 무응답자는 확정 시 참석자에 기본 포함
* "다음주"는 월요일 시작 달력 기준 다음 주
* 요일만 말하면 기준일 다음에 오는 그 요일 (기준일이 그 요일이면 다음 주). "이번주 X요일"은 기준일이 그 요일이면 당일
* 오전/오후 표기 없는 1\~7시는 오후
* 한 글자 요일("목", "수")은 다른 낱말일 수도 있어서, 대화 흐름에서 요일로 쓰였을 때만 날짜로 본다
* 제외 대상: 외부 일정(시험, 발표일), 과거 일정, 날짜 없는 막연한 약속("담에 놀러가자")

### 8.4 처리 파이프라인

```
메시지 저장 (AI 일정 도우미를 켠 프로젝트만)
  │
  ├─ ① 기다리기
  │     그 채널에 10초 동안 새 메시지가 없을 때만 실행 (협상 도중에는 돌리지 않는다)
  │
  ├─ ② 트리거 필터 (규칙)
  │     최근 메시지 5개에 날짜/시간/요일/약속 낱말이 없으면 스킵 → 비용 절감
  │
  ├─ ③ 대화 묶음 자르기 (규칙)
  │     최근 30개 메시지 중, 마지막으로 답한 카드 뒤와 8시간 공백 뒤의 메시지만
  │
  ├─ ④ 날짜 정규화 (규칙 기반)
  │     "다음주 화", "모레" → 그 메시지를 쓴 날 기준의 실제 날짜로 변환
  │     변환 결과를 메시지 뒤에 주석으로 붙여 LLM에 전달
  │
  ├─ ⑤ 상태 추적 LLM (Qwen2.5-7B + LoRA)
  │     누가 동의/반대했고 최종 결론이 뭔지 판단 → JSON 출력
  │
  └─ ⑥ 후처리
        JSON 검증 → 기존 캘린더와 대조 → 카드를 띄우거나, 건너뛰거나, 내린다
```

**설계 의도**: 날짜 계산은 LLM에 맡기지 않고 코드로 정확하게 처리한다. LLM은 대화 흐름 판단에만 집중한다.

**⑥ 후처리가 하는 일**

* 검증: 지난 날짜의 일정, 날짜와 요일이 맞지 않는 일정, 한 사람이 참석과 불참에 같이 들어간 일정은 버린다. 참여자가 아닌 이름은 뺀다. "8:00"처럼 오전인지 오후인지 알 수 없는 시각은 숫자로 넣지 않고 "8시"로 보여 준다
* 대조: 확정된 일정이 캘린더에 없으면 새 일정 카드, 같은 일정이 있는데 내용이 다르면 변경 카드, 취소가 확정되면 취소 카드를 만든다. 제안 중이거나 폐기된 일정은 카드를 만들지 않는다. 같은 날짜와 시각의 일정이 이미 캘린더에 있으면 새 일정 카드를 만들지 않는다
* 반복 막기: 이미 띄운 카드(무시한 카드 포함)와 내용이 같으면 다시 띄우지 않는다. 같은 날짜·시각 자리에는 카드를 한 장만 둔다
* 카드 내리기: 아직 답하지 않은 카드의 일정이 이어진 대화에서 폐기되거나 취소되면 그 카드를 자동으로 내린다. 같은 날짜와 시각으로 맞춰 보기 때문에, 시각이 숫자로 정해진 새 일정 카드와 변경 카드만 내린다. 취소 카드와 시각이 "저녁"처럼 말로만 적힌 카드는 내리지 않는다
* 모델 서버가 꺼져 있거나, 30초 안에 답하지 않거나, 답이 깨져 있으면 카드를 만들지 않는다. 채팅은 그대로 동작한다

**말로 고치기/추가하기 경로 (6.1)**: 사용자가 쓴 한 줄을 화자 = 요청한 팀원, 글 = `[요청] ` + 입력인 대화 한 턴으로 만들어 같은 ⑤ LLM에 보낸다. 기존 일정에는 고칠 카드의 일정(추가는 빈 목록)을 넣는다. 입력의 줄바꿈은 공백으로 바꿔 대화 턴을 더 만들 수 없게 한다. 모델이 꺼져 있거나 실패하거나 쓸 만한 답이 없으면 규칙 대체 경로를 쓴다: 날짜는 ④ 날짜 정규화, 시각은 오전/오후/저녁/밤이 붙었거나 24시간 표기이거나 1\~7시(오후로 본다)일 때만 숫자(아니면 "8시" 그대로 time_text), "장소는 X / X에서", "X 불참 / X는 못 와 / X 빼줘", "X도 와 / X 추가"(멤버 이름만). 규칙이 못 읽은 칸은 바꾸지 않고(추가는 비워 두고) 지어내지 않는다. 결과는 ⑥과 같은 검증(과거 날짜, 참석/불참 중복)을 거친다. 아무것도 못 알아들으면 바꾸지 않고 다시 말해 달라고 안내한다.

### 8.5 날짜 정규화 규칙

| 표현  | 규칙  |
|-----|-----|
| 오늘/내일/모레/글피 | 기준일 +0/+1/+2/+3 |
| X요일 (요일만) | 기준일 다음에 오는 X요일. 기준일이 X요일이면 다음 주 (수요일에 "수 보자" → 7일 뒤) |
| 이번주 X요일 | 기준일 이후 가장 가까운 X요일. 기준일이 X요일이면 당일 |
| 다음주 X요일 | 기준일이 속한 주(월 시작)의 다음 주 X요일 |
| 다다음주 X요일 | 다음 주 + 7일 |
| 이번 주말 | 이번 주 토요일 (토요일이 지났으면 일요일) |
| M/D, M월 D일 | 올해 기준, 이미 지났으면 내년 |
| "\~의 그 전주/다음주 X요일" | 기준이 되는 날짜로부터 상대 계산 |
| N시 (오전/오후 없음) | 1\~7시는 오후. 8\~11시는 숫자로 정하지 않고 "8시" 그대로 time_text에 보존 (되묻기는 만들지 않았다) |
| 오전, 아침, 새벽 / 오후, 저녁, 밤, 낮 | 오전과 오후를 정하는 데 쓴다 ("밤 12시"는 0시) |
| 한 글자 요일 (목, 수) | 후보로만 표시해 LLM에 넘긴다. 바로 뒤에 시각이 오면 요일로 확정한다. "목도리", "할 수 있어" 같은 낱말 안에서는 제외 |
| N시 반 | N:30 |
| 점심시간, 방과후, 수업 끝나고 | 숫자로 변환하지 않고 time_text에 보존 |

규칙 예시 270개를 `ml/common/dateparse_ko/examples.py`로 채점하고, 전부 통과한다.

### 8.6 데이터

**① 합성 학습 데이터 (계획 3,000\~5,000개 → 실제 10,237개, 라벨링 불필요)**


1. 코드로 정답 시나리오를 먼저 생성 (기준일, 참여자 3\~5명, 최종 결과, 번복 0\~2회, 불참자 여부, 날짜 표현 종류)
2. LLM에게 "이 시나리오대로 흘러가는 고등학생 팀 단톡을 만들어라"라고 요청
3. 정답을 알고 대화를 만들었으니 라벨이 자동으로 붙음
4. 다른 LLM이 시나리오를 보지 않고 대화만 읽어 답을 내고, 시나리오의 정답과 일치한 대화만 남긴다. 날짜 정규화기와 규칙으로도 검증한다

10,237개는 이전 모델까지 쓴 6,374개에 최종 모델용 3,863개를 더한 것이다. 최종 모델용에는 대화가 끝나기 전 중간 지점의 정답과, 말로 고치기용 한 줄 요청이 들어 있다.

생성 프롬프트 예시:

```
너는 고등학생 팀플 단톡 대화를 만드는 작가야.
아래 시나리오를 정확히 따르는 대화를 만들어.
- 기준일: 2026-10-12(월)
- 참여자: 민준, 서연, 지호, 하은
- 흐름: 민준이 수/목 중 투표 제안 → 서연 수, 지호 목
        → 서연이 목 저녁 가능하다고 수정 → 목 19:00 디스코드로 확정
- 날짜 표현: 요일만 사용 ("수", "목")
- 말투: 줄임말(ㅇㅋ, ㄱㄱ, ㄱㄴ), 오타, 짧은 문장
- 6~10턴, JSON 배열 [{"speaker":..,"text":..}]로만 출력
```

**② 실제 테스트셋 (100\~150개, 평가 전용): 아직 없다**

* 계획: 팀원/친구들이 시나리오 카드만 받고 자유롭게 단톡 역할극, 2명이 가이드라인대로 따로 라벨링하고 불일치한 건만 토론해서 확정, 학습에는 절대 사용하지 않음
* 지금: 시나리오 카드(120장 + 어려운 상황 24장)까지 만들었다. 역할극 대화와 라벨이 없다

**③ 파일럿 테스트셋 (20개, 1주차 가설 검증용): 카드만 있다**

* 유형: 단순 확정 3, 제안만 3, 번복 4, 취소 2, 부분 참석 3, 상대 날짜 3, 일정 아님 2
* 채점 스크립트는 `eval/schedule/score.py`다 (계획의 `score_pilot.py`는 만들지 않았다)

**④ 개발용 시험지 (AI가 작성, `eval` 레포)**

사람 테스트셋이 없어서 모델을 고를 때는 아래 시험지를 썼다. 대화와 정답을 모두 AI가 썼다.

| 시험지 | 건수 | 만든 방법 |
|---|---|---|
| 최종 시험 | 163건 (채널 대화 119 + 한 줄 요청 44) | 작성자가 학습 자료를 보지 않고 기획서와 서빙 코드만 보고 썼다. 다른 라벨러가 따로 정답을 달아 둘이 일치한 것만 채점한다. 모델을 돌리기 전에 파일을 고정했다 |
| 짧은 대화 세 묶음 | 72 / 40 / 50건 | 72건은 학습 데이터 생성기 밖에서 따로 썼다. 40건과 50건은 개발 중에 쓴 대화라 독립 시험지가 아니다 |
| 긴 대화 기록, 실사용 장면 | 70건 외 | 긴 대화와, 실제 화면으로 테스트한 장면에서 뽑은 대화 |

### 8.7 모델 구성

| 구분  | 모델  | 최종 시험 163건 |
|-----|-----|-----|
| 개선 전 기준선 (계획의 비교군 B) | Qwen2.5-3B-Instruct, Qwen2.5-7B-Instruct를 학습 없이 같은 프롬프트로 | 71건, 68건 |
| 이전 모델 | Qwen2.5-3B-Instruct + 날짜 정규화 + LoRA (v4) | 125건 |
| **최종 서비스 모델** | Qwen2.5-7B-Instruct + 날짜 정규화 + LoRA (v5, seed 42) | **147건** |
| 상용 최신 LLM 제로샷 (계획의 비교군 A) | 재지 않았다. `eval/schedule/run.py --target claude`로 잴 수 있게만 해 두었다 | - |

* 학습: 임대 GPU 서버에서 LoRA (r = 16, 2 에폭). 계획의 Colab이나 Mac은 쓰지 않았다
* 서빙: LoRA를 바탕 모델에 병합해 GGUF Q8_0로 바꾸고 llama.cpp 서버로 띄운다 (계획은 4bit 양자화). 응답은 temperature 0, JSON 형식, 최대 700토큰
* 후보는 7B seed 42, 7B seed 7, 같은 데이터로 학습한 3B였고 셋 다 채택 기준(8.8)을 넘었다. 미리 정한 규칙대로 7B를 골랐다
* seed는 규칙에서 벗어났다. 검증 손실이 낮은 쪽을 고르는 것이 규칙이었고 그 기준으로는 seed 7이다 (최종 시험도 148건으로 1건 높다). 그런데 seed 7은 같은 일정을 끝없이 되풀이한 응답이 한 번 있어서, 예외로 seed 42를 골랐다
* 한국어 특화 모델(EXAONE 등)과는 비교하지 않았다
* 가중치는 레포에 넣지 않고 비공개 Hugging Face 저장소에 둔다

### 8.9 가설 검증 (1주차)

**가설**: 범용 LLM은 ① 제안과 확정을 헷갈리고 ② 한국어 상대 날짜를 틀리고 ③ 번복/취소된 최종 결론을 놓친다.

**근거와 한계**: TimeBench(ACL 2024)에서는 GPT-4를 포함한 LLM이 시간 추론에서 사람보다 크게 뒤처졌고, Test of Time 벤치마크에서는 정보 제시 순서만 바꿔도 성능이 크게 달라졌다. 다만 둘 다 2024년 모델, 영어, 일반 시간 추론 기준이라 직접 측정이 필요하다.

**방법**: 파일럿 20개를 비교군 A, B에 같은 프롬프트(기준일 포함)로 넣고 `eval/schedule/score.py`로 채점

| 결과  | 개선 스토리 |
|-----|--------|
| 상용 LLM도 확정 F1 < 0.8 또는 오등록률 > 10% | **정확도 개선**: 내 모델이 상용 LLM보다 정확함 |
| 상용 LLM은 잘하고 소형 모델만 약함 | **효율 개선**: 상용 수준 정확도를 소형 모델로 달성 (비용 1/N, 속도 N배, 온디바이스 가능) |
| 둘 다 잘함 | **어려운 케이스 공략**: 번복 2회 이상, 긴 대화, 애매한 동의만 모은 하드셋에서 개선 |

**결과**: 이 검증은 계획대로 하지 못했다. 파일럿은 카드만 있고 대화가 없으며, 상용 LLM은 재지 않았다. 잰 것은 학습하지 않은 Qwen2.5뿐이다. 최종 시험 163건에서 3B는 71건, 7B는 68건(42\~44%)을 맞혔고 학습한 최종 모델은 147건(90.2%)이다. 그래서 지금 말할 수 있는 것은 "공개 소형 모델을 학습시켜 올린 폭"이고, 상용 LLM과 비교한 결과는 없다.

## 9. AI 2: 우회 욕설 검열

### 9.1 태스크 정의

* **입력**: 메시지 1개
* **출력**: 욕설 여부, 확률, 욕설 위치, 복원형 ("ㅅ1발" → "시발")

계획은 직전 메시지 2\~3개도 같이 보는 것이었다. 그렇게 학습시켰더니 평온한 대화 뒤에 나온 욕을 통과시키고 욕 뒤의 정상 문장을 가려서, 앞 메시지는 쓰지 않기로 했다. 서버는 앞 메시지를 받기는 하지만 판정에 쓰지 않는다.

### 9.2 처리 파이프라인

```
메시지
  ├─ ① 정규화
  │     전각/반각 통일, 영문 자판 치환(tlqkf → 시발), 기호 제거, 한 글자씩 띄운 말 붙이기,
  │     글자 사이 숫자·영문 잡음 제거, 자모 재조합, 반복 글자 줄이기
  ├─ ② 사전 찾기 (화이트리스트의 "시발점", "시발역" 같은 말은 건너뛴다)
  │     확실한 욕 목록에만 걸리면 모델을 부르지 않고 바로 가린다
  │     뜻이 여러 개인 말 목록에 걸리면 모델이 판단한다
  ├─ ③ KcELECTRA 파인튜닝 모델 (ONNX, CPU): 원문 + 정규화문 함께 판정
  │     점수가 민감도 기준 이상이면 욕 (느슨하게 0.9 / 보통 0.7 / 엄격하게 0.5)
  └─ ④ 저장: 욕 여부, 점수, 가릴 위치, 모델 버전을 메시지와 함께 저장
```

* 사전은 두 가지다. 확실한 욕 목록(약 300개와 발음 변형 약 2,900개)과 뜻이 여러 개인 말 목록(약 130개). 화이트리스트는 약 330개다
* 강조하려고 앞에 붙인 "개"("개웃기네")는 뒤에 오는 말 목록(약 130개)으로 따로 찾아 "개" 한 글자만 가린다. "찌개", "3개"처럼 낱말 끝의 "개"와 "개구리" 같은 다른 낱말은 그대로 둔다 (2026-11-27)
* 숫자와 영문을 모음으로 읽는 것 같은 더 과감한 읽기로도 사전을 찾는다. 여기서만 걸린 말은 뜻이 여러 개인 말로 다뤄 모델이 판단한다. 확실한 욕도 글자 사이를 띄어 썼으면 모델이 판단한다
* 모델을 쓸 수 없으면(설정하지 않았거나 오류) 뜻이 여러 개인 말도 가린다
* 사전에 없는데 모델만 욕으로 본 메시지는 욕의 위치를 알 수 없어서 메시지 전체를 가린다
* 띄어쓰기를 붙여서 생긴 욕("수박 씨 발아")은 원문으로 한 번 더 판정해 낮은 점수를 쓴다
* 프로젝트의 기본 민감도는 "엄격하게"다. 가리기 / 경고만 / 방장 알림은 화면에서 다르게 보여 줄 뿐이고 서버가 저장하는 판정은 같다

**결과**: 사람이 모은 C셋이 없어서 이 검증은 하지 못했다. 대신 위 399문장에서 공개 사전 필터가 욕의 절반 이상을 놓쳤고(재현율 0.461), 그래서 탐지율 개선 쪽으로 진행했다.

### 9.7 지속 개선 루프


1. 사용자 신고(오탐/미탐) 수집
2. 운영자 검수 후 학습 데이터에 추가
3. 재학습 후 A\~D 테스트셋으로 재평가
4. 성능이 오른 경우에만 배포, 대시보드에 버전별 기록

**지금**: 1번은 동작한다(신고가 DB에 쌓인다). 2번은 운영자 화면(웹 `/admin`, 2026-11-27)에서 가려진 메시지와 신고된 메시지를 5초마다 모아 볼 수 있다. 서버 `.env`의 운영자 비밀번호(`ADMIN_PASSWORD`)를 넣어야 열리고(10분에 10번 틀리면 잠김), 학습 데이터로 꺼내는 스크립트는 없다. 재학습은 직접 찾은 약점으로 v2부터 v5까지 했다. v5는 앞 메시지를 다시 보게 한 모델인데, 결과를 보기 전에 정한 조건을 넘지 못해서 4번 규칙대로 배포하지 않고 v4를 쓴다.

### 9.8 판정 기준

욕이 연상된다는 이유만으로 가리지 않는다. **특정 욕으로 복원되는지**를 기준으로 판단한다.

**청소년이 쓰는 메신저라서 욕설은 최대한 빡빡하게 잡는다** (2026-11-27 결정). 욕인지 아닌지 갈릴 때는 놓치는 쪽보다 잘못 가리는 쪽을 택한다. 잘못 가린 말은 [보기]로 볼 수 있고 [욕설 아님]으로 신고할 수 있지만, 놓친 욕은 그대로 보이기 때문이다.

* 모델이 놓치는 말은 사전에 넣어서 잡는다. 멀쩡한 글과 글자가 같아질 때만 모델에 맡긴다
* 사전에 넣을 때는 평가·학습 문장 전체에서 판정이 어떻게 바뀌는지 먼저 세어 보고, 잘못 가려지는 종류를 단어 파일의 주석에 적는다
* 판정 문턱을 낮추는 것은 효과가 없었다: 399문장에서 0.9부터 0.2까지 점수가 같다 (모델 점수가 0 아니면 1 근처에 몰려 있다)

| 구분 | 기준 | 예시 | 처리 |
|-----|-----|-----|-----|
| 우회 욕설 | 읽거나 발음하면 특정 욕으로 복원되고, 그 뜻으로 쓰임 | `너임마청년`("니 엄마 창년"의 발음 우회로 쓴 경우) | 가림 (label 1) |
| 닮은 정상 표현 | 글자나 소리만 욕과 비슷하고 욕의 뜻이 없음 | `청년`, `시발점`, `너 임마 청년이 그러면 되냐` | 통과 (label 0) |
| 비꼼, 암시 | 복원할 특정 욕이 없음 | 욕 없이 돌려 말하는 비꼼 | 자동 판정 제외, 신고 후 운영자 검수 (9.7) |

* 처리는 차단이나 처벌이 아니라 6.2의 가리기 + [보기]이고, 틀리면 [욕설 아님]으로 신고한다
* 맥락에 따라 욕일 수도 정상일 수도 있는 표현은 사전에서 바로 확정하지 않는다. 정규화가 공백을 지우므로 `너임마청년`을 그냥 넣으면 `너 임마 청년이 그러면 되냐`도 걸린다
* `너임마청년`, `니임마 청년`, `니엄마 청년`은 모델이 잡지 못해서(점수 0.001) 2026-11-27부터 사전(`badwords_phrase.txt`)에 넣었다. 붙여 쓴 것은 언제나 가린다. `니 임마 청년아`처럼 띄어 쓴 것도 가리고, `너 임마 청년이 그러면 되냐`, `니 엄마 청년 때 사진`처럼 뒤에 멀쩡한 글에서 오는 말이 이어질 때만 모델이 판정한다
* 다른 말 없이 혼자 쓴 `자지`, `보지`, `꼬추`, `잠지`는 가린다 (`badwords_alone.txt`). 문장 안에서는 모델이 판정한다 (`보지 마`). 2026-11-27에 `고추`, `장애인`, `니엄마`, `찢`, `찢기`, `앙앙`, `싼다`, `이기야`도 넣었다: 문장 안에서는 멀쩡한 말이지만 한 낱말만 보낸 메시지는 놀림인 경우가 많다 (`고추장 사 와`, `장애인 주차 구역`은 그대로 통과한다)
* **성적인 말, 고인 조롱과 혐오 말투, 사람을 낮춰 부르는 말도 가린다** (2026-11-27): `야동`, `애널`, `똥구멍`, `노무노무`, `부엉이바위`, `허버허버`, `돼지야`, `장애인이냐`. 공개 학습 데이터가 이런 말을 대부분 욕 아님으로 라벨해 두어서 모델이 놓치기 때문에 사전에 넣었다. 그래서 `원숭이 똥구멍은 빨개` 같은 멀쩡한 문장도 가려진다. 라벨이 달린 문장 39만 개에서 새로 가려진 정상 라벨 문장은 434개(0.14%)였고 대부분 성적인 낱말이 든 댓글이다
* 멤버 이름에 붙여 쓴 말(`강상우보지`, `상우 고추`)은 2026-11-27부터 규칙으로 가린다. 채팅 서버가 그 워크스페이스 멤버 이름을 필터에 넘기고, 필터는 이름을 같은 길이의 공백으로 지운 글을 사전으로 한 번 더 읽어서 걸린 곳을 더한다. 세 글자 한글 이름은 성을 뺀 두 글자(`상우`)도 지운다. 더하기만 하므로 이름 때문에 덜 가리는 일은 없고, 모델은 원문만 읽는다. 이름을 지운 나머지가 혼자 쓴 말일 때만 걸리므로 `상우야 그거 보지 마`, `강상우 화이팅`은 통과한다. `강상우 보지?`처럼 멀쩡할 수도 있는 글도 가려지고, `상우야 보지`처럼 조사가 붙으면 통과한다
* 사전으로 못 잡는 것: 신음 소리 같은 성적 표현(`하아앙`), 사람 이름을 욕처럼 쓰는 말. 성적인 말을 욕으로 라벨해 다시 학습한 v6는 2026-11-27에 기준을 넘지 못해 쓰지 않는다 (v4 유지)
* `개같네`처럼 붙여 쓴 `개같-`은 `개`를 가린다. `개 같이 산책`처럼 띄어 쓴 것은 모델이 판정하고, `번개같이`, `무지개같이`는 가리지 않는다
* **칭찬이나 놀림이어도 사람에게 쓴 비속어는 욕이다** (label 1): 친한 친구를 치켜세우거나 생김새를 놀리며 쓴 비속어도 같다. 동물이나 물건의 이름, 햇수처럼 뜻이 다르면 욕이 아니다 (label 0): `상어 아가리 모형`, `고양이 새끼 네 마리`, `5개년 계획`
* 문장에 동물이라는 말이 없이 `새끼`로만 부른 것은 동물을 보고 한 말이어도 욕으로 본다 (label 1)
* 강조하려고 앞에 붙인 `개`는 욕이다 (label 1, 2026-11-27): `개웃겨`, `개맛있어`. 화면에서는 `개` 한 글자만 가린다. 동물이나 다른 낱말의 `개`는 욕이 아니다 (label 0): `개 좋아해?`, `찌개`, `개구리`, `개편`
* 앞 대화를 봐야 아는 말은 앞 대화에 따라 라벨을 정한다. 앞 대화가 없어 알 수 없으면 `u`로 두고 빼거나 앞 대화를 붙인다
* 테스트셋에는 욕으로 쓴 `너임마청년`을 C(label 1), `너 임마 청년이 그러면 되냐`를 D(label 0)에 넣는다. 테스트 문장은 학습 데이터에 넣지 않는다

## 10. 시스템 설계

### 10.1 아키텍처

```
[브라우저]
     │  HTTPS
     ▼
[팀 서버 한 대 (Docker)]
     ├─ 웹: Next.js                      주소 /
     └─ 백엔드: FastAPI, 프로세스 1개    주소 /api
          ├─ 인증         이메일 로그인, JWT
          ├─ REST API     워크스페이스, 채널, 메시지, 일정, 할 일, 신고
          ├─ WebSocket    채널별 실시간 채팅, AI 카드 푸시
          ├─ 욕설 필터    사전 + ONNX 모델, CPU, 메시지를 저장하기 전에 판정
          ├─ 일정 추출    대화가 10초 멈추면 실행, 모델 서버를 HTTP로 호출
          └─ SQLite 파일
                 │  OpenAI 호환 API (/v1/chat/completions)
                 ▼
[GPU 서버 (임대)]
     └─ llama.cpp 서버 + 일정 모델 (GGUF)
```

* 메시지 저장 전에 서버 안에서 욕설 판정을 하고 결과를 같이 저장한 뒤 WebSocket으로 브로드캐스트
* 일정 추출은 채널별 디바운스 (마지막 메시지 후 10초. 대화가 이어지는 동안에는 돌리지 않는다: 협상 도중에 돌리면 정해지지 않은 시간으로 카드가 먼저 뜬다), 결과 카드는 WebSocket으로 푸시
* 계획의 "비동기 큐"는 따로 두지 않았다. 일정 추출은 백엔드 프로세스 안의 작업으로 돌고, 그래서 백엔드는 프로세스 1개로 띄운다
* 일정 모델 서버가 꺼져 있거나 답이 없으면 카드만 뜨지 않는다. 채팅, 캘린더, 욕설 필터는 그대로 동작한다
* 백엔드와 GPU 서버는 암호화된 터널로 잇고, 모델 서버를 인터넷에 직접 열지 않는다
* server와 web 레포의 main에 push하면 팀 서버가 Docker 이미지를 다시 빌드해 바꿔 띄운다
* `/moderate`와 `/schedule`은 평가 스크립트와 디스코드 봇이 쓰는 API다 (10.4)

### 10.2 기술 스택

| 영역  | 선택  | 이유  |
|-----|-----|-----|
| 프론트 | Next.js 16 + React 19 + Tailwind 4, shadcn, FullCalendar | 빠른 개발. Docker 이미지로 배포한다 (계획은 Vercel) |
| 백엔드 | FastAPI (Python 3.13) | 인증, REST API, WebSocket 실시간 채팅, AI 서빙을 파이썬 서버 하나로 |
| DB  | SQLite + SQLAlchemy(async, aiosqlite) + Alembic | 별도 DB 서버 없이 파일 하나, DATABASE_URL만 바꾸면 다른 DB로 이전 가능 |
| 욕설 모델 | KcELECTRA → ONNX | CPU에서도 빠름 |
| 일정 모델 | Qwen2.5-7B-Instruct + LoRA → GGUF Q8_0, llama.cpp 서버 | 계획은 2\~4B급 소형 모델 + 4bit였다. 정확도를 올리려고 7B로 바꿨고 GPU 서버가 필요해졌다 |
| 배포 | Docker, push하면 자동 배포, HTTPS 터널 | 팀 서버 한 대로 운영 |
| 실험 관리 | 모델별 예측과 채점 결과를 `eval` 레포에 파일로 보관 | 저장된 예측만으로 다시 채점할 수 있다 (계획의 W&B는 쓰지 않았다) |

### 10.3 DB 스키마

```
users(id, name, email, password_hash, created_at)
workspaces(id, name, invite_code, ai_schedule_on, ai_enabled_at,
           filter_mode('mask'|'warn'|'notify_admin'), filter_level(1~3, 기본 3))
members(workspace_id, user_id, role('owner'|'member'))
channels(id, workspace_id, name)
messages(id, channel_id, user_id, text, created_at, client_id,
         is_profane, profanity_score, profanity_spans, model_version)
events(id, workspace_id, title, date, start, time_text, location, status,
       attendees, absent, note, source('ai'|'manual'), source_message_ids)
ai_suggestions(id, channel_id, payload_json,
               action('added'|'edited'|'ignored', 대기 중이면 비어 있음), model_version, created_at)
reports(id, message_id, user_id, type('false_positive'|'missed'), text, created_at)
todos(id, workspace_id, title, assignee_id, due_date, done)
```

* `workspaces.ai_enabled_at`: AI 일정 도우미를 켠 시각. 이 뒤에 쓴 메시지만 분석한다
* `messages.client_id`: 같은 메시지를 다시 보내도 한 번만 저장되게 하는 번호
* `ai_suggestions.payload_json`: 카드 종류(add / update / cancel), 일정, 대상 일정 번호, 근거 메시지 번호. 말로 고친 카드는 AI가 처음 낸 일정도 담는다
* `reports`: 한 사람이 같은 메시지를 같은 종류로 두 번 신고할 수 없다. `text`에는 신고한 때의 메시지 글을 같이 저장한다
* ai_suggestions.action과 reports는 재학습/평가 데이터로 쓰려고 만든 칸이다. 지금은 저장만 한다 (11장). action의 ignored에는 서버가 자동으로 내린 카드와 다른 카드에 답해서 쓸모없어진 카드도 들어 있어서, 데이터로 쓰려면 사람이 누른 것과 구분하는 칸이 필요하다. 취소 카드의 [일정 취소하기]는 added로 기록된다

### 10.4 API 명세

서비스 API (웹앱이 호출, 로그인 토큰 필요):

```
POST            /auth/signup, /auth/login                → JWT 발급
GET             /auth/me
GET/POST        /workspaces
GET/PATCH       /workspaces/{id}                         (설정 변경은 방장만)
GET             /workspaces/{id}/members
GET/POST        /invites/{code}                          (미리 보기 / 참가)
GET/POST        /workspaces/{id}/channels
GET/POST        /channels/{id}/messages                  (보내기는 저장 전에 욕설 판정)
GET/POST        /workspaces/{id}/events                  PATCH/DELETE /events/{id}
GET/POST        /workspaces/{id}/todos                   PATCH/DELETE /todos/{id}
GET             /channels/{id}/suggestions               (답을 기다리는 카드)
POST            /suggestions/{id}/action                 (added | edited | ignored, 이미 답한 카드면 409)
POST            /suggestions/{id}/revise                 {"text": "8시로 바꿔줘"} → 고친 카드 + 바뀐 칸 (대기 중 카드만)
POST            /workspaces/{id}/events/parse            {"text": "내일 7시 회의"} → 일정 추가 창에 채울 초안 (저장 안 함)
POST            /reports                                 (false_positive | missed)
WS              /ws/channels/{id}                        실시간 수신
```

* WebSocket은 연결한 뒤 첫 메시지로 토큰을 보내 인증한다. 인증에 실패하거나 토큰이 만료되면 서버가 연결을 닫는다 (코드 1008)
* WebSocket으로 오는 것: 새 메시지(`message`), 새 카드나 고쳐진 카드(`suggestion`), 처리되거나 내려간 카드(`suggestion_resolved`), 새 멤버(`member_joined`), 설정 변경(`workspace_updated`), 일정 변경(`events_changed`)
* 요청 본문은 1MiB까지다. 멤버가 아닌 프로젝트의 자료는 404로 답한다

AI API (평가 스크립트와 디스코드 봇이 호출, `X-API-Key` 필요):

```
POST /moderate
요청: {"text": "시1발 뭐하냐", "context": ["..."], "level": 2}
응답: {"is_profane": true, "score": 1.0, "spans": [[0, 3]],
       "restored": "시발 뭐하냐", "model_version": "dict"}

POST /schedule
요청: {"ref_datetime": "2026-10-12T21:05+09:00",
       "participants": ["민준","서연","지호","하은"],
       "dialogue": [{"speaker":"민준","text":"그럼 목 7시 디코","ts":"..."}],
       "existing_events": [...]}
응답: {"events": [ ...8.2 형식... ], "model_version": "v5-7b-s42"}
```

* `context`는 받기만 하고 판정에 쓰지 않는다 (9.1). `level`은 민감도 1\~3이다. `names`(없어도 된다)는 워크스페이스 멤버 이름이고, 이름에 붙여 쓴 말을 찾는 데 쓴다. `model_version`은 사전만으로 판정하면 `dict`, 모델이 판정하면 모델 이름이다
* 지금 배포한 서버에서 채팅 메시지는 이 API를 거치지 않고 백엔드 안에서 같은 함수로 판정한다. 설정에 따라 같은 코드를 띄운 다른 서버의 `/moderate`에 맡길 수도 있다

## 11. 개인정보와 안전

* 사용자 대부분이 미성년자라서 대화 분석 동의를 명시적으로 받는다. 프로젝트를 만드는 사람은 온보딩에서 체크하고(기본은 꺼짐), 초대받은 사람은 참가하기 전에 안내를 읽고 [동의하고 참가]를 누른다. 사용자별 동의 기록은 따로 남기지 않는다
* 일정 AI는 워크스페이스 단위로 방장이 켜고 끌 수 있다. 켠 뒤에 쓴 메시지만 분석한다
* 욕설 필터는 끌 수 없고 모든 메시지에 적용된다. 동의 안내문은 일정 AI만 말하고 욕설 판정은 말하지 않는다 (보완 필요)
* 실제 대화 원문은 학습에 쓰지 않는다. 학습은 합성 데이터와 공개 데이터만 썼고, 화면에도 "AI 학습에 쓰지 않아요"라고 안내한다
* 신고와 카드 버튼 결과는 저장만 하고 학습에 쓰지 않는다. 계획은 동의한 경우에 익명화해서 재학습에 쓰는 것이었다. 그렇게 하려면 동의를 받는 화면, 익명화, 꺼내는 도구를 먼저 만들고 안내문도 고쳐야 한다
* 운영자 화면(`/admin`)에서는 모든 팀의 가려진 메시지와 신고된 메시지 원문, 보낸 사람 이름이 보인다. 가려지지 않고 신고도 없는 메시지는 보이지 않는다. 동의 안내문에는 아직 이 내용이 없다 (보완 필요)
* 계획은 욕설 탐지 로그를 30일만 보관하는 것이었다. 지금은 지우는 기능이 없어서 메시지와 판정 결과가 계속 남는다. 메시지 삭제와 회원 탈퇴 기능도 서버에 없다
* 서비스는 자체 모델로만 운영한다. 일정 모델은 우리가 띄운 모델 서버에서, 욕설 모델은 백엔드 안에서 돌아서 대화가 외부 AI 서비스로 나가지 않는다. 상용 LLM은 합성 학습 데이터를 만드는 스크립트와 비교 평가 스크립트에서만 쓰고, 여기에 실제 사용자 대화는 넣지 않는다
* 일정 모델 서버는 우리가 빌려서 운영하는 GPU 서버다. 동의 안내문은 "우리 서버 안에서만 분석"이라고 하는데, 임대 서버도 여기에 든다는 점을 안내문에 밝힐지 정해야 한다
* 비밀번호는 해시(argon2)로 저장하고, 로그인 토큰은 7일 뒤 만료된다

### 16.4 이렇게 나누는 이유

* 날짜 정규화(dateparse_ko)를 학습과 서빙이 같은 레포에서 import하므로 결과가 어긋나지 않는다
* 담당이 레포 단위로 나뉜다: 화면은 web, 백엔드와 AI는 server
* 시험지와 정답은 공개 레포에 두면 학습 자료에 섞일 수 있어서 비공개 레포(eval)로 뺐다
* DB 스키마, 인증, 실시간 채팅까지 전부 server(FastAPI)가 맡는다. web은 API와 WebSocket만 호출한다

### 16.5 두 레포 사이 API 규칙


1. server의 Pydantic 스키마(`schemas.py`)를 API 형식의 기준으로 삼는다
2. FastAPI가 만드는 openapi.json에서 web 쪽 TypeScript 타입을 자동 생성한다 (openapi-typescript 등)
3. API 형식을 바꾸는 server PR에는 web 담당(A)을 리뷰어로 넣는다

### 16.6 데이터 커밋 규칙

| 구분  | 커밋 여부 | 이유  |
|-----|-------|-----|
| 테스트셋 (파일럿, 실제, C, D) | 커밋    | 작고 재현 불가, 평가 기준. 지금 server에는 시나리오 카드, C 예시, D 초안까지만 있다 |
| 개발용 시험지 (AI 작성) | `eval` 레포(비공개)에 커밋 | 모델을 고를 때 쓴 근거 |
| 합성 데이터 | gitignore | 스크립트로 재생성 가능 |
| 공개 데이터 원본 | gitignore | 라이선스, 용량 |
| 모델 가중치 | gitignore | HF Hub에 버전별 업로드 |

## 17. 역할 분담 (4인: 전문가 1 + 초보자 3)

* 초보자: 입력/출력이 명확하고, 튜토리얼을 따라 할 수 있고, 결과를 바로 확인할 수 있는 일을 맡는다

### 17.2 파트 1. 전문가: 아키텍처 + 일정 AI 핵심 + 통합

* API 스키마(`schemas.py`) 확정
* 일정 AI 핵심: 합성 데이터 생성기, LoRA 파인튜닝, 상태 추적(`tracker.py`), 기존 일정 대조(`reconcile.py`)

* 욕설 AI 학습: KcELECTRA 파인튜닝(1차/2차), ONNX 변환, /moderate 서빙. 학습 데이터는 파트 3이 만들어 넘긴다
* 초보자 지원: 모든 PR 코드 리뷰, 파트별 템플릿 코드 제공, 주 1회 30분 페어 작업

**산출물**: 레포 뼈대, DB 마이그레이션, /schedule API, 학습된 일정 모델, 학습된 욕설 모델(ONNX), 통합된 데모

### 17.3 파트 2. 초보자: 웹 화면 (Next.js)

**맡는 이유**: 결과가 바로 눈에 보여서 배우기 좋다. 어려운 실시간 연결은 전문가가 훅으로 만들어주므로 화면만 만들면 된다.

**할 일**

* 로그인, 온보딩(워크스페이스 생성, 초대 링크, 대화 분석 동의)

* 할 일 목록 화면
* AI 일정 카드 UI (추가/수정/무시 버튼)

**완료 기준**: 더미 데이터로 모든 화면이 동작하고, 전문가가 준 훅/API를 연결하면 실제 데이터가 보인다.

### 17.4 파트 3. 초보자: 욕설 AI

**맡는 이유**: 증강 규칙은 파이썬 문자열 처리라 초보자도 할 수 있다. GPU 학습과 ONNX 변환처럼 환경 문제로 막히기 쉬운 모델 학습은 파트 1이 맡는다.

**할 일**

* 공개 데이터 수집, 정리 (라이선스 확인 포함)
* 증강 규칙 10종 구현 (숫자 치환, 자모 분리, 초성화 등). 규칙마다 입력/출력 예시를 정리
* 1단계 사전 필터 + 화이트리스트("시발점", "18세" 등)
* 학습 데이터(`train.jsonl`) 만들기: 공개 데이터 + 증강 결과를 합쳐 파트 1에 넘긴다. 학습은 파트 1이 한다
* 테스트셋 C(친구들 대상 "필터 뚫기 챌린지"), D(오탐 유도 문장 100개) 수집
* 기존 필터 vs 내 모델 성능 비교
* 파트 1이 학습/변환한 모델을 테스트셋 A\~D로 채점하고, 약점을 정리해 2차 학습 데이터에 반영

**완료 기준**: 테스트셋 A\~D 점수표가 나오고, /moderate에 문장을 넣으면 판정 결과가 나온다.

**미리 공부할 것**: 파이썬 문자열/정규식, 한글 자모 분해(jamo, hgtk 라이브러리), jsonl 파일 다루기

### 17.5 파트 4. 초보자: 날짜 규칙 + 테스트 데이터 + 발표

**맡는 이유**: 날짜 정규화는 규칙이 8.5에 다 정해져 있어서, 입력/정답 예시대로 나오게 만들면 되는 명확한 일이다. 데이터 제작과 평가는 코딩보다 꼼꼼함이 중요하다.

**할 일**

* 1주차 가설 검증: 파일럿 20개를 ChatGPT/Claude에 넣고 `eval/schedule/score.py`로 채점
* 날짜 정규화 모듈(dateparse_ko): "다음주 화", "모레", "이번 주말" 등 규칙 구현 + 입력/정답 예시 100개 이상
* 실제 테스트셋 제작: 시나리오 카드 만들기 → 팀원/친구 역할극 → 가이드라인대로 라벨링 (전문가와 교차 검수)
* 평가 실행: 버전별 점수 CSV 정리, 개선 전후 그래프
* 디스코드 봇 (플랜 B, discord.py로 AI 서버 호출만 하면 됨)
* 발표 자료, 시연 시나리오 담당

**완료 기준**: 날짜 예시 100개 전부 정답, 실제 테스트셋 100개 이상 완성, 발표 자료 완성

**미리 공부할 것**: 파이썬 datetime, 8.3 가이드라인

### 17.7 초보자 막힘 방지 규칙

* 전문가가 파트마다 템플릿 코드 + 입력/출력 예시를 먼저 준다. 초보자는 빈칸만 채우면 되게 한다
* 하루 이상 막히면 바로 공유한다. 혼자 붙잡지 않는다
* PR은 작게 올리고, 전문가가 리뷰한 뒤 머지한다

### 17.8 AI 사용 규칙

AI(Claude Code, ChatGPT, Codex 등)는 써도 된다. 대신 무엇을 시켰고 무엇이 바뀌었는지 전부 남긴다.

1. **모든 AI 세션은 본인 파트 폴더에 남긴다**: server, web 레포의 `ai-sessions/part1` \~ `part4`. 프롬프트, AI 답변, 바뀐 코드(diff)를 모두 기록한다
2. **Claude Code는 자동 기록된다**: 레포를 클론한 뒤 한 번만 `git config ai.part part3`(본인 파트 번호)를 실행하면, 프롬프트를 보낼 때마다 `ai-sessions/part3/날짜_세션.md`에 쌓인다 (`.claude/settings.json` 훅)
3. **다른 도구는 직접 남긴다**: ChatGPT 웹 등은 `ai-sessions/README.md`의 양식대로 같은 폴더에 붙여 넣는다
4. **로그는 코드와 같은 PR에 커밋한다**: AI로 만든 코드인데 로그가 없으면 머지하지 않는다
5. **AI가 짠 코드는 본인이 설명할 수 있어야 한다**: 리뷰에서 설명 못 하면 다시 짠다
6. **넣으면 안 되는 것**: `.env`, API 키, 비밀번호, 실제 사용자 대화. 테스트셋(파일럿, 실제, C, D)은 합성 데이터 생성이나 학습 프롬프트에 넣지 않는다
