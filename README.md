# 팀플메이트 최종 기획서

> 대화만 하면 AI가 확정된 약속을 캘린더에 올려주고, 우회 욕설까지 걸러주는 학생 팀 전용 협업 플랫폼

* 버전: v1.0 (최종)
* 가정: 팀원 3명, 개발 기간 8주

## 1. 개요

| 항목  | 내용  |
|-----|-----|
| 서비스명 | 팀플메이트 (가칭) |
| 한 줄 소개 | 채팅 + 캘린더 + 할 일을 하나로 묶고, AI 2개가 일정 정리와 욕설 검열을 대신 해주는 협업 공간 |
| 타깃  | 중고등학생/대학생 팀 프로젝트, 동아리, 스터디 (3\~6명) |
| 핵심 AI | ① 대화 기반 일정 생성 AI ② 우회 욕설 검열 AI |
| 개발 방향 | 기존 AI의 약점을 직접 측정하고, 개선하고, 다시 측정해서 개선 폭을 수치로 증명 |

## 2. 추진 배경과 문제 정의

### 2.1 문제


1. **일정이 대화 속에 묻힌다**: 팀플 일정은 "화요일 어때?" → "난 안 돼" → "그럼 목 7시?" → "ㅇㅋ"처럼 여러 턴에 걸쳐 정해진다. 누군가 따로 정리하지 않으면 놓치고, 번복되면 옛날 일정이 그대로 남는다.
2. **학생 공간의 욕설/비방**: 학생 커뮤니티에서는 욕설이 흔하고, 사전 기반 필터는 "ㅅ1발", "씨@발", "tlqkf" 같은 우회 표현을 못 막는다.

### 2.2 페르소나

* **팀장 민준 (고2)**: 단톡에서 정한 회의 시간을 매번 공지로 다시 정리해야 함. 빼먹으면 누군가 안 옴.
* **팀원 서연 (고2)**: 학원 때문에 시간이 자주 바뀜. "그래서 언제로 정해졌어?"를 자주 물어봄.
* **동아리 운영진 하은 (고3)**: 동아리 채팅의 욕설/비방 관리가 부담. 기존 필터는 우회 표현을 못 막음.

## 3. 경쟁 분석과 차별점

### 3.1 기존 서비스

| 서비스 | 하는 것 | 빈틈  |
|-----|------|-----|
| 잔디  | 대화방/메시지 요약, 메시지를 업무로 전환 (AI 기능은 유료 인텔리전스 플랜 전용) | 기업용 유료, 대화에서 일정을 자동 확정하지 않음 |
| Slack + n8n 자동화 | 메시지에서 시간/날짜/장소를 파싱해 구글 캘린더 초대 생성 | 메시지 1개 기준이라 여러 턴 협상, 번복, 취소를 못 따라감 |
| 네이버 클린봇 | 기호/문자를 활용한 우회 악플까지 대응하도록 지속 업그레이드 | 네이버 서비스 내부 전용 |
| 무료 욕설 필터 API | 정규식 + 비속어 DB + 아호코라식 기반 (상업용은 월 약 7만 원 KISO API 권장) | 새로운 우회 표현에 약함 |
| 카카오톡 단톡 | 학생들이 실제로 쓰는 곳 | 일정 정리, 필터링 기능 없음 |

### 3.2 차별점


1. 메시지 1개가 아니라 **대화 흐름 전체**를 보고 확정, 번복, 취소를 판단
2. 사전 필터가 못 잡는 **우회 욕설** 탐지 + 오탐 방지
3. 학생 팀이 **무료로** 쓰는 가벼운 협업 공간
4. 사용자 피드백으로 **AI가 계속 개선되는 구조**

## 4. 목표와 성공 기준

### 4.1 서비스 목표

* 우회 욕설이 채팅방에 노출되지 않음

### 5.2 핵심 원칙

**AI는 자동 등록하지 않고 항상 제안만 한다.**

* 잘못 등록되는 피해를 막는다
* 사용자가 누른 버튼(추가/수정/무시)이 그대로 평가 및 재학습 데이터가 된다

## 6. 사용자 흐름

### 6.1 일정 자동 등록


1. 팀원들이 채널에서 일정 협상
2. AI가 확정을 감지하면 채팅에 카드 표시: "[일정] 10/15(목) 19:00 · 디스코드 · 팀 회의 / 참석: 민준, 서연, 지호, 하은 / [캘린더에 추가] [수정] [무시]"
3. [캘린더에 추가]를 누르면 캘린더에 등록되고 카드가 "등록됨"으로 바뀜
4. 이후 "목요일 회의 취소하자"가 확정되면 "10/15 회의를 취소할까요?" 카드 표시

### 6.2 욕설 필터


1. 메시지 전송 시 서버에서 판정 (100ms 이내)
2. 욕설이면 "부적절한 표현이 가려졌어요 [보기]"로 표시
3. 오탐이면 [욕설 아님], 미탐이면 메시지 메뉴의 [욕설 신고]로 신고

## 8. AI 1: 대화 기반 일정 생성

### 8.1 태스크 정의

* **입력**: 최근 대화 20\~30턴 (화자, 텍스트, 시각) + 기준 날짜/요일 + 참여자 목록 + 기존 캘린더 일정
* **출력**: 일정 후보 목록과 각 후보의 상태

### 8.2 출력 형식

```
{
  "events": [
    {
      "title": "팀 회의",
      "date": "2026-10-15",
      "weekday": "목",
      "start": "19:00",
      "time_text": null,
      "location": "디스코드",
      "status": "confirmed",
      "attendees": ["민준", "서연", "지호", "하은"],
      "absent": [],
      "note": null
    }
  ]
}
```

* status: proposed(제안 중) / rejected(폐기) / confirmed(확정) / cancelled(취소)
* 시각이 숫자가 아니면 start는 null로 두고, 원문 표현은 time_text에 저장 (예: "점심시간")

### 8.3 정답 기준 가이드라인

**확정 조건 (둘 중 하나)**


1. 마지막 수정안에 대해 제안자 포함 과반이 동의하고 반대가 없음 (4명이면 3명)
2. 제안자나 팀장의 명시적 확정 선언("이걸로 확정", "그럼 그때 보자") + 1명 이상 동의

**세부 규칙**

* 불참 선언자는 absent에 넣고, 늦은 합류는 참석으로 보고 note에 기록
* 무응답자는 확정 시 참석자에 기본 포함
* "다음주"는 월요일 시작 달력 기준 다음 주
* 요일만 말하면 기준일 이후 가장 가까운 그 요일
* 오전/오후 표기 없는 1\~7시는 오후
* 제외 대상: 외부 일정(시험, 발표일), 과거 일정, 날짜 없는 막연한 약속("담에 놀러가자")

### 8.4 처리 파이프라인

```
대화 버퍼 (최근 20~30턴)
  │
  ├─ ① 트리거 필터 (규칙)
  │     날짜/시간/요일/약속 키워드가 없으면 스킵 → 비용 절감
  │
  ├─ ② 날짜 정규화 (규칙 기반)
  │     "다음주 화", "모레", "이번 주말" → 실제 날짜로 변환
  │     변환 결과를 대화에 주석으로 붙여 LLM에 전달
  │
  ├─ ③ 상태 추적 LLM (소형 모델 + LoRA)
  │     누가 동의/반대했고 최종 결론이 뭔지 판단 → JSON 출력
  │
  └─ ④ 후처리
        JSON 검증, 기존 캘린더와 대조, 카드 생성
```

**설계 의도**: 날짜 계산은 LLM에 맡기지 않고 코드로 정확하게 처리한다. LLM은 대화 흐름 판단에만 집중한다.

### 8.5 날짜 정규화 규칙

| 표현  | 규칙  |
|-----|-----|
| 오늘/내일/모레/글피 | 기준일 +0/+1/+2/+3 |
| (이번주) X요일 | 기준일 이후 가장 가까운 X요일 |
| 다음주 X요일 | 기준일이 속한 주(월 시작)의 다음 주 X요일 |
| 다다음주 X요일 | 다음 주 + 7일 |
| 이번 주말 | 이번 주 토/일 |
| M/D, M월 D일 | 올해 기준, 이미 지났으면 내년 |
| "\~의 그 전주/다음주 X요일" | 기준이 되는 날짜로부터 상대 계산 |
| N시 (오전/오후 없음) | 1\~7시는 오후, 8\~11시는 문맥 판단 (애매하면 되묻기) |
| N시 반 | N:30 |
| 점심시간, 방과후, 수업 끝나고 | 숫자로 변환하지 않고 time_text에 보존 |

### 8.6 데이터

**① 합성 학습 데이터 (3,000\~5,000개, 라벨링 불필요)**


1. 코드로 정답 시나리오를 먼저 생성 (기준일, 참여자 3\~5명, 최종 결과, 번복 0\~2회, 불참자 여부, 날짜 표현 종류)
2. LLM에게 "이 시나리오대로 흘러가는 고등학생 팀 단톡을 만들어라"라고 요청
3. 정답을 알고 대화를 만들었으니 라벨이 자동으로 붙음
4. 날짜 정규화기와 규칙으로 자동 검증하고, 안 맞는 건 버림

생성 프롬프트 예시:

```
너는 고등학생 팀플 단톡 대화를 만드는 작가야.
아래 시나리오를 정확히 따르는 대화를 만들어.
- 기준일: 2026-10-12(월)
- 참여자: 민준, 서연, 지호, 하은
- 흐름: 민준이 수/목 중 투표 제안 → 서연 수, 지호 목
        → 서연이 목 저녁 가능하다고 수정 → 목 19:00 디스코드로 확정
- 날짜 표현: 요일만 사용 ("수", "목")
- 말투: 줄임말(ㅇㅋ, ㄱㄱ, ㄱㄴ), 오타, 짧은 문장
- 6~10턴, JSON 배열 [{"speaker":..,"text":..}]로만 출력
```

**② 실제 테스트셋 (100\~150개, 평가 전용)**

* 팀원/친구들이 시나리오 카드만 받고 자유롭게 단톡 역할극
* 2명이 가이드라인대로 따로 라벨링하고, 불일치한 건만 토론해서 확정
* 학습에는 절대 사용하지 않음

**③ 파일럿 테스트셋 (20개, 1주차 가설 검증용)**

* pilot_schedule_testset.jsonl 사용 (채점: score_pilot.py)
* 유형: 단순 확정 3, 제안만 3, 번복 4, 취소 2, 부분 참석 3, 상대 날짜 3, 일정 아님 2

### 8.7 모델 구성

| 구분  | 모델  | 역할  |
|-----|-----|-----|
| 비교군 A | 상용 최신 LLM 제로샷 (GPT/Claude/Gemini 중 1\~2개) | 최고 성능 기준선 |
| 비교군 B | 소형 오픈 모델 제로샷 (EXAONE, Qwen 계열 2\~4B급) | 개선 전 기준선 |
| 내 모델 | 비교군 B + 날짜 정규화 + LoRA 파인튜닝 | 최종 서비스 모델 |

* 학습: Colab (T4/L4) 또는 Mac(MLX)
* 서빙: 4bit 양자화

### 8.8 평가 지표

| 지표  | 정의  |
|-----|-----|
| 확정 일정 F1 | 날짜, 시간, 상태가 모두 맞은 확정 일정 기준 |
| 오등록률 | 확정이 아닌 것을 확정으로 낸 비율 (가장 중요) |
| 날짜 정확도 | 뽑힌 일정 중 날짜가 맞은 비율 |
| 취소 감지율 | 취소 정답 중 맞힌 비율 |
| 지연시간/비용 | 요청당 응답 시간, 1,000회당 비용 |

결과는 유형별로 나눠서 보고한다. 그래야 어디가 약하고 어디가 좋아졌는지 보인다.

### 8.9 가설 검증 (1주차)

**가설**: 범용 LLM은 ① 제안과 확정을 헷갈리고 ② 한국어 상대 날짜를 틀리고 ③ 번복/취소된 최종 결론을 놓친다.

**근거와 한계**: TimeBench(ACL 2024)에서는 GPT-4를 포함한 LLM이 시간 추론에서 사람보다 크게 뒤처졌고, Test of Time 벤치마크에서는 정보 제시 순서만 바꿔도 성능이 크게 달라졌다. 다만 둘 다 2024년 모델, 영어, 일반 시간 추론 기준이라 직접 측정이 필요하다.

**방법**: 파일럿 20개를 비교군 A, B에 같은 프롬프트(기준일 포함)로 넣고 score_pilot.py로 채점

| 결과  | 개선 스토리 |
|-----|--------|
| 상용 LLM도 확정 F1 < 0.8 또는 오등록률 > 10% | **정확도 개선**: 내 모델이 상용 LLM보다 정확함 |
| 상용 LLM은 잘하고 소형 모델만 약함 | **효율 개선**: 상용 수준 정확도를 소형 모델로 달성 (비용 1/N, 속도 N배, 온디바이스 가능) |
| 둘 다 잘함 | **어려운 케이스 공략**: 번복 2회 이상, 긴 대화, 애매한 동의만 모은 하드셋에서 개선 |

## 9. AI 2: 우회 욕설 검열

### 9.1 태스크 정의

* **입력**: 메시지 1개 (+ 직전 메시지 2\~3개)
* **출력**: 욕설 여부, 확률, 욕설 위치, 복원형 ("ㅅ1발" → "시발")

### 9.2 처리 파이프라인

```
메시지
  ├─ ① 정규화
  │     전각/반각 통일, 반복 문자 축약, 공백 제거 버전 생성,
  │     숫자/특수문자 → 한글 후보 치환, 자모 재조합
  ├─ ② 1단계 사전 필터 (아호코라식): 확실한 욕설은 즉시 차단
  ├─ ③ 2단계 KcELECTRA 파인튜닝 모델: 원문 + 정규화문 함께 판정
  └─ ④ 화이트리스트 후처리: "시발점", "18세", "수박씨 발라" 등 오탐 방지
```

### 9.3 우회 변형 증강 규칙

| 유형  | 예시  | 구현  |
|-----|-----|-----|
| 숫자 치환 | 시1발, 18 | 글자 사이 숫자 삽입/치환 |
| 특수문자 삽입 | 씨@발, 시.발 | 랜덤 위치 삽입 |
| 자모 분리 | ㅅㅣ발 | 음절을 자모로 분해 |
| 받침 분리 | 시ㅂ알 | 종성을 떼어 다음 글자로 |
| 초성화 | ㅅㅂ, ㅂㅅ | 초성만 남기기 |
| 띄어쓰기 쪼개기 | 시 발 | 음절 사이 공백 |
| 유사 발음 | 씨발, 쉬발, 시바 | 발음 사전 치환 |
| 영문 자판/로마자 | tlqkf, sibal | 두벌식 자판 매핑, 로마자화 |
| 늘이기 | 시이이발 | 모음 반복 |
| 복합  | 씨@1발 | 위 규칙 2\~3개 조합 |

정상 문장도 같은 방식으로 변형해서 넣는다. 변형됐다고 다 욕은 아니라는 것을 학습시켜서 오탐을 막는다.

### 9.5 평가

| 테스트셋 | 내용  | 목적  |
|------|-----|-----|
| A. 원문 | 공개 데이터 테스트 분할 | 기본 성능 유지 확인 |
| B. 자동 변형 | 증강 규칙으로 변형한 문장 (학습에 안 쓴 것) | 규칙 커버리지 |

* 비교군: 오픈소스 사전 필터 / 공개 욕설 분류 모델 / 내 모델
* 지표: F1(A\~C), 오탐률(D), 응답 시간

### 9.6 가설 검증 (1주차)

C 테스트셋 30개를 먼저 모아서 사전 필터와 공개 모델에 넣어본다.

* 우회 탐지율이 낮게 나오면 그대로 개선 스토리로 간다
* 이미 높으면 오탐률 개선이나 속도(ONNX, CPU 서빙) 쪽으로 무게를 옮긴다

### 9.7 지속 개선 루프


1. 사용자 신고(오탐/미탐) 수집
2. 운영자 검수 후 학습 데이터에 추가
3. 재학습 후 A\~D 테스트셋으로 재평가
4. 성능이 오른 경우에만 배포, 대시보드에 버전별 기록

## 10. 시스템 설계

### 10.1 아키텍처

```
[Next.js 웹앱]
     │  REST API + WebSocket
     ▼
[백엔드 서버: FastAPI]
     ├─ 인증         이메일 로그인, JWT
     ├─ REST API     워크스페이스, 채널, 메시지, 일정, 할 일, 신고
     ├─ WebSocket    채널별 실시간 채팅, AI 카드 푸시
     ├─ /moderate    욕설 필터 (ONNX, CPU, 동기 처리)
     └─ /schedule    일정 추출 (소형 LLM, 비동기 큐)
     │
     ▼
[SQLite]
```

* 메시지 저장 전에 서버 안에서 욕설 판정을 하고 결과를 같이 저장한 뒤 WebSocket으로 브로드캐스트
* 일정 추출은 채널별 디바운스 (마지막 메시지 후 10초 또는 5턴마다), 결과 카드는 WebSocket으로 푸시

### 10.2 기술 스택

| 영역  | 선택  | 이유  |
|-----|-----|-----|
| 프론트 | Next.js + Tailwind | 빠른 개발, Vercel 배포 |
| 백엔드 | FastAPI | 인증, REST API, WebSocket 실시간 채팅, AI 서빙을 파이썬 서버 하나로 |
| DB  | SQLite + SQLAlchemy(async, aiosqlite) + Alembic | 별도 DB 서버 없이 파일 하나, DATABASE_URL만 바꾸면 다른 DB로 이전 가능 |
| 욕설 모델 | KcELECTRA → ONNX | CPU에서도 빠름 |
| 일정 모델 | 소형 LLM + LoRA, 4bit | 저비용 학습/서빙 |
| 실험 관리 | W&B 또는 CSV 로그 | 버전별 성능 기록 |

### 10.3 DB 스키마

```
users(id, name, email, password_hash, created_at)
workspaces(id, name, invite_code, ai_schedule_on, filter_mode, filter_level)
members(workspace_id, user_id, role)
channels(id, workspace_id, name)
messages(id, channel_id, user_id, text, created_at,
         is_profane, profanity_score, profanity_spans, model_version)
events(id, workspace_id, title, date, start, location, status,
       attendees, absent, source('ai'|'manual'), source_message_ids)
ai_suggestions(id, channel_id, payload_json,
               action('added'|'edited'|'ignored'), model_version, created_at)
reports(id, message_id, user_id, type('false_positive'|'missed'), created_at)
todos(id, workspace_id, title, assignee_id, due_date, done)
```

ai_suggestions.action과 reports가 그대로 재학습/평가 데이터가 된다.

## 11. 개인정보와 안전

* 사용자 대부분이 미성년자라서 대화 분석 동의를 온보딩에서 명시적으로 받는다
* 일정 AI는 워크스페이스 단위로 켜고 끌 수 있다
* 실제 대화 원문은 학습에 쓰지 않는다. 학습은 합성 데이터와 공개 데이터만 쓰고, 신고 데이터는 동의한 경우에만 익명화해서 사용한다
* 욕설 탐지 로그는 신고 검수용으로 30일만 보관한다
* 상용 LLM API는 비교 평가에만 쓰고, 서비스 운영은 자체 모델로 해서 대화가 외부로 나가지 않게 한다

## 14. 기대 효과

### 16.4 이렇게 나누는 이유

* 날짜 정규화(dateparse_ko)를 학습과 서빙이 같은 레포에서 import하므로 결과가 어긋나지 않는다
* CI가 단순하다: web은 lint/build, server는 pytest/평가
* 담당이 레포 단위로 나뉜다: 화면은 web, 백엔드와 AI는 server
* DB 스키마, 인증, 실시간 채팅까지 전부 server(FastAPI)가 맡는다. web은 API와 WebSocket만 호출한다

### 16.5 두 레포 사이 API 규칙


1. server의 Pydantic 스키마(`schemas.py`)를 API 형식의 기준으로 삼는다
2. FastAPI가 만드는 openapi.json에서 web 쪽 TypeScript 타입을 자동 생성한다 (openapi-typescript 등)
3. API 형식을 바꾸는 server PR에는 web 담당(A)을 리뷰어로 넣는다

### 16.6 데이터 커밋 규칙

| 구분  | 커밋 여부 | 이유  |
|-----|-------|-----|
| 테스트셋 (파일럿, 실제, C, D) | 커밋    | 작고 재현 불가, 평가 기준 |
| 합성 데이터 | gitignore | 스크립트로 재생성 가능 |
| 공개 데이터 원본 | gitignore | 라이선스, 용량 |
| 모델 가중치 | gitignore | HF Hub에 버전별 업로드 |

## 17. 역할 분담 (4인: 전문가 1 + 초보자 3)

12장의 3인 분담을 4인 기준으로 대체한다.

* 전문가: 제일 어렵고 막히면 전체가 멈추는 부분(구조, 일정 AI 핵심, 통합)을 맡는다
* 초보자: 입력/출력이 명확하고, 튜토리얼을 따라 할 수 있고, 결과를 바로 확인할 수 있는 일을 맡는다

### 17.1 한눈에 보기

| 파트  | 담당  | 비중  | 난이도 | 레포  |
|-----|-----|-----|-----|-----|
| 1   | 전문가: 아키텍처 + 일정 AI 핵심 + 통합 | 약 40% | ★★★★★ | web, server |
| 2   | 초보자: 웹 화면 | 약 20% | ★★☆☆☆ | web |
| 3   | 초보자: 욕설 AI | 약 20% | ★★★☆☆ | server |
| 4   | 초보자: 날짜 규칙 + 테스트 데이터 + 발표 | 약 20% | ★★☆☆☆ | server |

### 17.2 파트 1. 전문가: 아키텍처 + 일정 AI 핵심 + 통합

**맡는 이유**: 설계가 틀리면 다 같이 막히는 부분이고, LLM 파인튜닝은 초보자가 하기 어렵다.

**할 일**

* 두 레포 뼈대, 폴더 구조, CI, .env 관리
* FastAPI 백엔드: DB 스키마(SQLAlchemy + Alembic), 인증(이메일 + JWT), 서비스 REST API, WebSocket 실시간 채팅
* web 쪽 API 래퍼와 실시간 훅(`useMessages` 등). 화면은 파트 2가 만든다
* API 스키마(`schemas.py`) 확정
* 일정 AI 핵심: 합성 데이터 생성기, LoRA 파인튜닝, 상태 추적(`tracker.py`), 기존 일정 대조(`reconcile.py`)
* 통합: 메시지 저장 → 욕설 판정/일정 추출 → WebSocket으로 카드 표시까지 전체 흐름 연결
* 욕설 모델 ONNX 변환과 서빙을 파트 3과 함께 작업
* 초보자 지원: 모든 PR 코드 리뷰, 파트별 템플릿 코드 제공, 주 1회 30분 페어 작업

**산출물**: 레포 뼈대, DB 마이그레이션, /schedule API, 학습된 일정 모델, 통합된 데모

### 17.3 파트 2. 초보자: 웹 화면 (Next.js)

**맡는 이유**: 결과가 바로 눈에 보여서 배우기 좋다. 어려운 실시간 연결은 전문가가 훅으로 만들어주므로 화면만 만들면 된다.

**할 일**

* 로그인, 온보딩(워크스페이스 생성, 초대 링크, 대화 분석 동의)
* 채널 목록, 채팅 화면(메시지 목록, 입력창)
* 캘린더 화면 (FullCalendar 같은 라이브러리 사용)
* 할 일 목록 화면
* AI 일정 카드 UI (추가/수정/무시 버튼)
* 욕설 가림 UI ("가려진 메시지 [보기]"), 신고 버튼
* 설정 화면 (AI on/off, 필터 모드/민감도)
* AI 성능 대시보드 (CSV를 차트로)

**완료 기준**: 더미 데이터로 모든 화면이 동작하고, 전문가가 준 훅/API를 연결하면 실제 데이터가 보인다.

**미리 공부할 것**: Next.js App Router 기초, Tailwind, shadcn/ui, fetch로 REST API 호출하기

### 17.4 파트 3. 초보자: 욕설 AI

**맡는 이유**: 증강 규칙은 파이썬 문자열 처리라 초보자도 할 수 있다. 학습도 HuggingFace 튜토리얼 수준이라 따라 하기 쉽다.

**할 일**

* 공개 데이터 수집, 정리 (라이선스 확인 포함)
* 증강 규칙 10종 구현 (숫자 치환, 자모 분리, 초성화 등). 규칙마다 입력/출력 예시 테스트 작성
* 1단계 사전 필터 + 화이트리스트("시발점", "18세" 등)
* KcELECTRA 파인튜닝 (전문가가 준 Colab 노트북 템플릿 사용)
* 테스트셋 C(친구들 대상 "필터 뚫기 챌린지"), D(오탐 유도 문장 100개) 수집
* 기존 필터 vs 내 모델 성능 비교
* ONNX 변환과 /moderate 서빙은 전문가와 같이 작업

**완료 기준**: 테스트셋 A\~D 점수표가 나오고, /moderate에 문장을 넣으면 판정 결과가 나온다.

**미리 공부할 것**: 파이썬 문자열/정규식, 한글 자모 분해(jamo, hgtk 라이브러리), HuggingFace Trainer 튜토리얼

### 17.5 파트 4. 초보자: 날짜 규칙 + 테스트 데이터 + 발표

**맡는 이유**: 날짜 정규화는 규칙이 8.5에 다 정해져 있어서, 테스트부터 쓰고 통과시키면 되는 명확한 일이다. 데이터 제작과 평가는 코딩보다 꼼꼼함이 중요하다.

**할 일**

* 1주차 가설 검증: 파일럿 20개를 ChatGPT/Claude에 넣고 score_pilot.py로 채점
* 날짜 정규화 모듈(dateparse_ko): "다음주 화", "모레", "이번 주말" 등 규칙 구현 + 단위 테스트 100개 이상
* 실제 테스트셋 제작: 시나리오 카드 만들기 → 팀원/친구 역할극 → 가이드라인대로 라벨링 (전문가와 교차 검수)
* 평가 실행: 버전별 점수 CSV 정리, 개선 전후 그래프
* 디스코드 봇 (플랜 B, discord.py로 AI 서버 호출만 하면 됨)
* 발표 자료, 시연 시나리오 담당

**완료 기준**: 날짜 테스트 전부 통과, 실제 테스트셋 100개 이상 완성, 발표 자료 완성

**미리 공부할 것**: 파이썬 datetime, pytest, 8.3 가이드라인

### 17.7 초보자 막힘 방지 규칙

* 전문가가 파트마다 템플릿 코드 + 입력/출력 예시를 먼저 준다. 초보자는 빈칸만 채우면 되게 한다
* 하루 이상 막히면 바로 공유한다. 혼자 붙잡지 않는다
* PR은 작게 올리고, 전문가가 리뷰한 뒤 머지한다
